## New findings

**1. `leads_homes.json.gz` is stale relative to `history_homes.json.gz` - 4 real, newly-scraped homes.bg listings are currently invisible to the site/Supabase sync, silently, with no error.**
`sync_to_supabase.py` reads only `leads_*.json` (documented at `docs/backlog.md:4938`), never `history_*.json`. The most recent scheduled scrape commit, `6ec6324` ("Update listings", 2026-09-27 13:56:45Z), updated `history_homes.json.gz` (added 30 new listing IDs, all `first_seen` today) but did **not** touch `leads_homes.json.gz` at all (absent from that commit's diff stat) - the currently-committed `leads_homes.json.gz` is 3 minutes older (commit `ae73794`, 13:53:24Z). 4 of those 30 new IDs never made it into leads at all: `homes_hs297039` (Къща, 625m², София - град, 3,000,000 EUR), `homes_as1705003` (Двустаен, 69m², жк. Зона Б5, София, 240,000 EUR), `homes_hs298837` (Къща, 105m², Център, София, 228,000 EUR), `homes_hs298836` (Къща, 900m², к.к.Слънчев Бряг, Несебър, 1,680,000 EUR) - all present and fully populated in `history_homes.json.gz`, none in `leads_homes.json.gz`. Two more (`homes_hs298691`, `homes_as1704991`) made it into leads but lost their photo the same way despite history having a real photo URL for both. This is exactly the "silently drops listings/fields instead of failing loudly" bug class - the commit succeeded (green, no error) but the leads regen step for homes.bg (and possibly olx.bg/bcpea.org - their leads files also weren't touched in that same commit, though their current leads/history ID sets happen to still match 1:1, so impact there can't be confirmed the way it can for homes.bg) silently didn't run or didn't get committed.

**2. Systemic bad-geocode-cache regression: previously-identified-and-purged wrong coordinates are back in `data/geocode_cache.json`, now propagating across multiple portals to ~1,470+ listings (excluding a separate false-positive noted below).**
`docs/backlog.md` item 28.3 (2026-09-23) documents that entries including "Братя Миладинови", "Родина 2/3", and "Цветница" were confirmed wrong and **deleted** from `data/geocode_cache.json` that day. Today, all three are back in the cache with the *identical* wrong coordinates:
- `"Братя Миладинови, Бургас, България"` → `{lat: 42.1507015, lng: 24.7384211}` - that point is in Plovdiv oblast, not Burgas. 149 imot.bg listings + 159 homes.bg listings, ALL tagged `city: "Бургас"`, `area: "Братя Миладинови"` (a real Burgas district), now sit at this Plovdiv point (e.g. `imot_1b174919589666346`, https://www.imot.bg/obiava-1b174919589666346-prodava-dvustaen-apartament-grad-burgas-bratya-miladinovi).
- `"Родина 2, Русе, България"` and `"Цветница, Русе, България"` similarly wrong again (e.g. `imot_1b178878000592331`, Русе/Родина 2, resolves into `haskovo` oblast; `imot_1b178479696030488`, Русе/Цветница, into `targovishte` oblast).
Beyond these 3 recurrences, many more area-name cache entries share the same signature (city-qualified query resolving to a real BUT UNRELATED Bulgarian city, shared identically by two independent portals - imot.bg and homes.bg both hit `"Зона Б, Велико Търново, България"` → the same wrong Burgas-area point, 54+54 listings combined): `Опълченски`/Стара Загора→Пловдив, `Граф Игнатиев`/Ямбол→Пловдив, `Гео Милев`/Видин→Пловдив, `Медковец`/Враца→Монтана, `Плиска`/Видин→Шумен, `Рилци`/Добрич→Благоевград, `Грамада`/Благоевград→Видин, `Беленци`/Габрово→Ловеч, `Болярово`/Хасково→Ямбол, `Самуил`/Враца→Стара Загора, `Сениче`/Враца→Стара Загора, and more.
Total scope via a strict city-name-vs-coordinate-oblast cross-check (`sync_to_supabase.oblast_key_from_latlng()` vs. `CITY_KEY_TO_OBLAST`, excluding the known-benign sofia/sofia_grad satellite-town pairs like Боровец/Божурище/Правец which resolve correctly via geo and are NOT a bug): imot.bg 680, homes.bg 512, olx.bg 222, alo.bg 7, bazar.bg 2, imoti.bg 2 listings. This corrupts displayed location/province filtering AND `findComparables()`'s haversine radius matching (same mechanism as yesterday's alo.bg overseas-centroid finding) - e.g. the 149 "Братя Миладинови" Burgas listings would show each other as 0km-apart "comparables" while actually being ~200km apart. Could not verify the *current* correct coordinate for each live (network blocked), but the internal evidence is strong: identical, real (non-random) coordinates shared by dozens of listings independently tagged with a real, specific, correctly-spelled district name in a *different* city, for entries that were already independently confirmed wrong and deleted 4 days ago per the repo's own backlog. This is a regression of a previously-fixed issue, not a new one - worth someone checking why the purge didn't hold (a re-geocode of the same ambiguous query reproducing the same bad Nominatim result seems most likely, per `geo_utils.py`'s own `Geocoder` class caching by exact query string with no re-verification once cached).

**3. `extract_coords_imoti_net()`'s known-but-deliberately-deferred regex bug (docs/backlog.md item 28.1, "still open ... needs live network access") is not an isolated 2-listing issue - it's actively corrupting hundreds of imoti.net listings, growing since 2026-09-23.**
577 imoti.net listings (`data/leads.json`) across 14 different real cities share the *exact same* coordinate `(42.6960693142, 23.3253958611)` (a real Sofia point): 236 tagged Пловдив, 68 Бургас, 28 Варна, 9 Враца, 8 Стара Загора, plus Пазарджик/Ловеч/Благоевград/Хасково/Шумен/Русе/Плевен/Габрово - only the 212 tagged София are plausibly correct. This value doesn't appear in `data/geocode_cache.json` at all, consistent with `geo_utils.py`'s comment that imoti.net coordinates come from a raw regex (`_IMOTI_NET_LAT_RE`/`_IMOTI_NET_LNG_RE`, `re.search` = first match only) against `"latitude"`/`"longitude"` JSON keys anywhere in each listing's own detail-page HTML - if the page has more than one such key (e.g. a "similar/nearby listings" widget) before the listing's own block, the first (wrong, generic) one wins. Backlog item 27 already one-time-corrected 654 such bad coordinates as pure data on 2026-09-23 but explicitly left the regex itself unfixed pending live HTML access; the fact that essentially the same-sized problem (577) exists again today, for what are largely different listing IDs than the original batch (first-seen dates span well past 2026-09-23), confirms it has kept quietly recurring on every newly-scraped imoti.net listing since. Yesterday's report describing "2 isolated Pleven listings in France/Hungary" as isolated should be corrected - that's the same root cause, just two records that happened to match a rarer (foreign) generic latitude/longitude block instead of the common Sofia one.
