ONE FINDING, HIGH SEVERITY - live and unaddressed on main right now:

## imoti.net's "100%-apartment" miscategorization bug (already fixed once in PR #199) has been silently reintroduced for ~65% of listings

**Current state (HEAD 7b591e1):** 17,680 of imoti.net's 27,251 committed listings (data/history.json and data/leads.json) again carry `"category": "apartment"` - a value the current classifier can never legitimately produce. `category_classifier.classify_listing()` (imported and used correctly by the current `scraper.py`, confirmed by reading it) only ever returns one of `garage/shop/business/land/house/flat` - "apartment" isn't in its vocabulary at all. So every one of these 17,680 records is provably wrong, not just suspicious.

Concrete examples currently in `data/leads.json` (all imoti.net's own URL slugs, which the project's own PR #199 already established as a reliable ground-truth signal):
- `imoti.net` id `6005389` - url `.../parcel/6005389/`, title "Development land, 500 м2 Sofia, Gotse Delchev" -> stored `category: "apartment"`, `category_confidence: "high"`. Should be `land`.
- id `6237422` - url `.../garaj/6237422/`, title "Garage, 34 м2 Sofia, Vitosha" -> stored `category: "apartment"`. Should be `garage`.
- id `6147232` - url `.../kashta/6147232/`, title "House, 160 м2 Sofia, Knyajevo" -> stored `category: "apartment"`. Should be `house`.
- id `6282516` - url `.../etaj-ot-kashta/6282516/`, title "Floor of a house, 137 м2 Plovdiv, Center" -> stored `category: "apartment"`. Should be `house`.
(Live portal pages couldn't be fetched to double-confirm - imoti.net is blocked in this sandbox - but the URL-slug-as-ground-truth method is the same one PR #199 itself used and verified, not a new/unvetted method.)

**Root cause, traced with git archaeology, not guessed:** PR #199 (merged 2026-09-22T16:15:40Z) fixed this correctly - confirmed `git show aacb170:data/history.json` shows 0/26,881 "apartment" right after merge. Four hours later, commit `d76d607` ("Update listings (large sites)", 2026-09-22 20:04:11Z) reintroduced it: `git show d76d607:data/history.json` shows 17,680/27,251 "apartment" again. Direct before/after diff on listing `6005389` proves the mechanism:
- Before (`5c9c9ea`, post-fix): `category: "land"`, snapshots ending `2026-09-22T10:42:15Z`.
- After (`d76d607`): `category: "apartment"`, a *new* snapshot appended at `2026-09-22T17:27:37Z` (a genuinely fresh scrape - the URL's own `page=` param changed too), correct category silently lost.

This is `merge_history_conflict.py` - the merger built and shipped *today* specifically to fix the unrelated alo.bg dead-crawl incident - doing exactly what it was designed to do, but with an unintended side effect it wasn't tested against: it picks which side of a `git pull --rebase` conflict's `"latest"` dict wins per-listing by comparing **scrape-timestamp recency** (`freshest_seen_at`), not **code-correctness recency**. A long-running `scrape-large.yml` job that checked out `main` *before* PR #199 merged, ran for hours using the old pre-fix `scraper.py`, and only hit its rebase conflict against `main` *after* PR #199 had already landed, produces a `latest` dict with a chronologically newer `seen_at` than PR #199's own data-only backfill commit (which corrected `category` in place without adding a new snapshot at all) - so the merger picks the *stale, buggy* run's `category` as the winner. This is a generic risk, not a one-off: any correctness-only data fix (touches `latest` fields without adding a snapshot) landing while a long scrape job is mid-flight is vulnerable to being silently clobbered the same way, on any of the `history*.json` files this merger now covers (it applies uniformly by filename pattern, not just to `history_alo.json`).

**Live-site consequence, not just a data-quality footnote:** `index.html`'s `CATEGORY_TO_BUCKET` maps `apartment: 'flat'` (line ~2485), and `TYPE_BUCKET_CATEGORIES.flat = ['apartment', 'flat']` (line ~4359) - both deliberately written to tolerate the *old* vocabulary. So right now, on the live site: all ~17,680 of these garages/houses/land parcels display under the "Flats" type-filter button and are invisible under "Garages"/"Houses"/"Land" where they belong, and `findComparables()`'s same-category radius/price-average feature (`index.html` ~3387-3419) mixes them into "flat" comparables for real flats near them - a direct instance of the "comparables that mix property categories" bug class.

Nothing in `docs/decisions.md` or the backlog currently reflects that this regressed - the 2026-09-22 entry for PR #199 still reads as the settled, correct state.
