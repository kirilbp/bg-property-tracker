## Important limitation this run — worse than the documented accepted gap

Missy's standing instructions say only `*.supabase.co` is unreachable from this sandbox and that `WebFetch` "should be unaffected." That was **not true this run**: every `WebFetch` call failed with `EGRESS_BLOCKED`, including the three portal domains needed (`www.imoti.net`, `sales.bcpea.org`, `imoti.bg`) **and** a neutral control domain (`example.com`). So this wasn't portal-specific — outbound web access was blocked network-wide for this session, not just to Supabase.

Net effect: no sampled listing could be cross-checked against its live source page, which is the core verification step. Flagging plainly rather than guessing. Today's audit is weaker than usual — it only covers internal-consistency checks within the committed JSON itself, not source-vs-stored comparison.

## Finding: internal data mismatch (verified without needing network access — both values come from the same stored record)

- **Listing:** `bcpea_91911`, portal `sales.bcpea.org`, https://sales.bcpea.org/properties/91911 (land near Колю Мариново, Братя Даскалови, Стара Загора)
- **File/location:** `data/leads_bcpea.json`, record starting at line 39957
- **What's wrong:** The structured `"sqm"` field stores `300`, but the scraper's own `"description"` field (scraped from the same source page, same record) states the parcel's documented area as **3300 кв.м**:
  > "...с площ от 3300 кв.м, находящ се в село Колю Мариново..."

  There's only one area figure in this description (unlike many bcpea records that legitimately cite several areas for sub-parts of a property, e.g. main unit + garage + ideal parts), so this isn't a case of picking the wrong sub-area — it's a straight mismatch between the numeric field and the scraper's own text for the same parcel, off by roughly 11x (consistent with a dropped digit, e.g. "3.300" being misparsed as "300" during a locale/thousands-separator conversion). This would misstate the parcel size by ~11x anywhere `sqm` or `price_per_sqm` is surfaced for this listing. Since this looks like a parsing-pipeline bug rather than a one-off typo on the source page, it's worth checking whether the same digit-drop pattern affects other `sales.bcpea.org` land records where area is given as "X.XXX кв.м" with a period-based thousands separator.
  - Could not confirm the true area against the live page itself this run (network blocked), so can't rule out the description text itself being wrong rather than `sqm` — but since both values are the scraper's own output for the same field, it's at minimum an internal inconsistency worth a human look.
