## New findings today

**1. imot.bg: 486 active listings silently lost their description on the most recent regen, despite the portal's own detail-page scrape having it.**
Cross-checking `leads_imot.json` against `history_imot.json`'s own `latest` snapshot (which records `detail_checked: true` plus the real description text) turned up 486 listings where the current lead has `description: null` and `detail_checked: null`/missing, but `history_imot.json[id].latest` has both `detail_checked: true` and a full description string, dated the exact same day. All 486 share an identical `first_seen: "2026-09-25T08:27:49..."` (a single batch) and all are `source_status: "active"` today - not removed/relisted listings where a reset would make sense.
Examples:
- `imot_1q176908925254514` - https://www.imot.bg/obiava-1q176908925254514-prodava-hotel-oblast-lovech-gr-apriltsi-vidima - history's `latest.description` starts "Продава се атрактивен имот в гр. Априлци, кв. 'Видима'..."; current lead has `description: null`.
- `imot_1j177434859820256` - https://www.imot.bg/obiava-1j177434859820256-prodava-kashta-oblast-lovech-gr-lukovit - history's `latest.description` starts "Продава се двуетажна къща 130 кв.м. с гараж..."; current lead has `description: null`.
This is a silent field drop on an already-successfully-scraped field, affecting a whole batch, not an isolated case like yesterday's single imoti.net photo.

**2. olx.bg: 786 listings (713 still active) silently lost their photo, spread across a month of first-seen dates.**
Same cross-check method on `leads_olx.json` vs `history_olx.json`: 786 listings where history's `latest.photo` has a real CDN URL but the current lead has `photo: null`. Unlike the imot.bg case, this isn't one batch - first-seen dates spread from 2026-08-25 through 2026-09-25 (e.g. 440 from 2026-08-25, 79 from 2026-09-25, dozens more scattered across ~15 other dates in between), suggesting an ongoing/recurring drop rather than a single incident.
Examples:
- `olx_9bo3S` - `source_status: active`, current `photo: null`; history's `latest.photo` = `https://frankfurt.apollo.olxcdn.com:443/v1/files/rzoxmsy3fsnu3-BG/image;s=216x152;q=50`.
- `olx_9Fetx`, `olx_9Q6jW` - same pattern, both active, both with a real photo URL in history's latest snapshot but `null` in the current lead.

**3. alo.bg: ~134 overseas listings share exact duplicate "country-centroid" coordinates instead of real per-listing geocoding, which would corrupt the comparables/radius feature for them.**
alo.bg carries some overseas listings (Greece, Turkey, Romania, UAE, France, Spain, Cyprus - holiday/investment properties marketed to Bulgarian buyers). 194 alo.bg listings have lat/lng outside Bulgaria's bounding box; of those, 134 share one of 7 exact-duplicate coordinate pairs matching well-known "geographic center of country" points: `(39.074208, 21.824312)` × 88 listings (Greece), `(38.963745, 35.243322)` × 26 (Turkey), `(45.943161, 24.96676)` × 7 (Romania), `(23.424076, 53.847818)` × 6 (UAE), `(46.227638, 2.213749)` × 3 (France), `(40.463667, -3.74922)` × 2 (Spain), `(35.126413, 33.429859)` × 2 (Cyprus). Example: `alo_11329809` (Halkidiki, Greece, https://www.alo.bg/nea-plagiya-halkidiki-garciya-apartament-81m2-11329809) and 87 other, unrelated Greek listings all sit at the exact same point. This matters beyond a map-pin cosmetic issue: `index.html`'s `findComparables()` (lines ~3870-3887) computes real-distance (haversine) comparables and includes any listing with lat/lng regardless of country - these overseas listings would show up as 0km-apart "comparables" of each other purely from the geocoding fallback, not real proximity.

**4. imoti.net: 2 Pleven, Bulgaria listings have coordinates in France and Hungary respectively (distinct root cause from #3 - not a shared fallback, just wrong).**
- `6291116` - https://www.imoti.net/en/obiava/prodava/pleven/gradska-chast/tristaen/6291116 - `city: "Плевен"`, but `lat: 46.947743577, lng: 1.6612637042` - central France (near Bourges), ~2,000km from Pleven.
- `6291119` - https://www.imoti.net/en/obiava/prodava/pleven/mara-dencheva/tristaen/6291119 - `city: "Плевен"`, but `lat: 47.9208017841, lng: 19.7362589817` - Budapest, Hungary.
Both precise-looking (many decimal places), not a shared fallback point like finding #3 - looks like an individual geocoding mismatch. Only 2 found across all 8 portals' full lat/lng ranges, reporting as isolated but concrete.
