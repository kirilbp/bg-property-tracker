## Finding 1 - "relisted_from" relisting links matching different properties, worst on alo.bg (price-history/relisting integrity bug)

Scope: checked every `price_history` entry with a `relisted_from` field across bazar.bg (2,069 links), alo.bg (13 links), imot.bg (54 links), olx.bg (2 links) by comparing the linked pair's area/city/sqm.

- **alo.bg - clearest case, single source fans into 5 unrelated listings in 4 different cities.** `alo_10705202` (https://www.alo.bg/era-viva-predlaga-prostoren-tristaen-apartament-v-centara-na-sofiya-10705202 - a Sofia-center 3-room flat, removed 2026-08-23, price 284,931 EUR, `sqm: null`) is recorded as the `relisted_from` source for:
  - `alo_11178758` - Стара Загора, Център, 44,000 EUR, "Боксониера 25 кв.м." (a studio/boxroom)
  - `alo_9305963` - Шумен, Център, 133,000 EUR
  - `alo_11284088` - Бургас, Център, 125,000 EUR
  - `alo_11373924` - Кюстендил, Център, 243,100 EUR
  - `alo_11114697` - Бургас, Център, 259,000 EUR
  Five different cities, five different prices, none matching the source's 284,931 EUR or Sofia location. The only thing they share is `area: "Центъа"/"Център"` (a generic name every Bulgarian town has) and `sqm: null`. A second alo.bg source, `alo_11327046` (Sofia/Люлин-Център), similarly fans into a Бургас listing and a separate Пловдив listing. This looks like the matcher is keying on too weak a signature (generic area name + missing sqm) when alo.bg data lacks `sqm`, and is falsely tagging unrelated properties as the same relisted unit - which would show a fabricated "price dropped from €284,931 to €44,000" badge on a Stara Zagora studio that has nothing to do with the Sofia flat.
  - 8 of alo.bg's 13 total `relisted_from` links show this kind of area/city mismatch.

- **bazar.bg - same pattern, smaller rate but same-city examples that are clearly not the same unit.** 133 of 2,069 `relisted_from` links (6.4%) show an area mismatch. Two concrete examples where price and room-count both differ substantially, ruling out "just a boundary-adjacent neighborhood":
  - `bazar_56204143` (Шумен, 5-ти полк, 172,000 EUR, 3-стаен) linked as relisted from `bazar_55681991` (Шумен, Боян Българанов 2, 214,500 EUR, 3-стаен) - different, non-adjacent Shumen neighborhoods, €42,500 apart.
  - `bazar_56220807` (София, Дружба 2, 293,000 EUR, 3-стаен) linked as relisted from `bazar_55477512` (София, Белите брези, 432,000 EUR, 4-стаен) - Druzhba (east Sofia) vs Belite Brezi (southwest Sofia), different room count, €139,000 apart.
  - Also verified one bazar.bg pair the opposite way as a sanity check (`bazar_55922729`/`bazar_55483740`): both listings' photo filenames share the identical numeric image-set id (`1b178548403086875_*`), so this specific pair probably is genuinely the same photos re-posted - but the title/area still changed from "2-СТАЕН, Център" to "3-СТАЕН, Цветен квартал" between the two records, which the price-history badge doesn't surface at all.

- **imot.bg - lower confidence this is our bug, flagging for awareness rather than as confirmed.** 7 of 54 links show mismatches, but at least two pairs share the identical numeric id suffix across a lettered type-prefix (e.g. `imot_1r174152771753869` "parcel" / `imot_1j174152771753869` "house", both Перник/Бела вода; `imot_1t178725733110588` "business" / `imot_1n178725733110588` "warehouse", identical price €600,000 and identical 816 sqm) - this looks like it could be imot.bg's own convention of the same seller cross-posting one property under two category tabs with a shared base id, which I can't confirm without reaching imot.bg directly. Worth a second look by whoever owns `detect_relistings.py`, but I'm not calling it a confirmed bug the way the alo.bg/bazar.bg cases are.

This is squarely a "relisting tagged incorrectly" issue per my checklist - it inflates/fabricates price-drop percentages and "relisted" badges between properties that aren't the same listing.

## Finding 2 - alo.bg category field misclassifying apartments as garage/shop/business/land (filter-correctness bug)

Checked every alo.bg, imot.bg, olx.bg, and imoti.net listing whose stored `category` is non-`flat` (garage/shop/business/land) against its own scraped URL slug for apartment-type keywords (`apartament`, `dvustaen`, `tristaen`, `chetiristaen`, `mnogostaen`, `ednostaen`) - the URL slug is the portal's own text, captured by the scraper itself, so this isn't a guess about the live page.

- **alo.bg: 598 of 91,399 listings** (0.65%) have an apartment-type URL slug but a non-flat category. 166 of those are tagged `category_confidence: "high"` (the classifier claiming certainty while wrong), split: 125 tagged "garage", 23 "business", 14 "land", 4 "shop". Examples:
  - `alo_11287679` - https://www.alo.bg/prostoren-tristaen-apartament-s-dve-parkomesta-v-kompleks-skai-driims-11287679 - "spacious three-room apartment with two parking spaces" - stored as `category: garage`, confidence `high`.
  - `alo_11401745` - https://www.alo.bg/nov-dvustaen-apartament-s-podzemno-parkomyasto-i-morska-gledka-do-plaja-na-kavaci-sozopol-11401745 - "new two-room apartment with underground parking space" - stored as `category: garage`, confidence `high`.
  - `alo_10963345` / `alo_11083076` - "Нов двустаен апартамент" (new two-room apartment) in Панорама Парк Изток - both stored as `category: business`, confidence `high`.
  This means the site's "garage"/"shop"/"business" filters currently surface hundreds of actual apartments, and the "flat" filter is missing them.
- **olx.bg**: 36 mismatches, all `category: land` at confidence `low` (already self-flagged as uncertain) - all ground-floor apartments described as having their own yard/veranda ("parteren apartament s dvor"), a genuinely ambiguous case, not miscategorized with false confidence. Lower severity, noting for completeness only.
- **imot.bg and imoti.net (leads.json)**: 0 mismatches found by this check - clean.

## Finding 3 - single dropped photo, imoti.net listing 6157650 (minor, isolated)

`data/history.json`'s own `latest` snapshot for `6157650` (https://www.imoti.net/en/obiava/prodava/sofia/poduene/garaj/6157650/ - garage, Poduene, Sofia, 47 sqm, active) has `photo: "https://www.imoti.net/web/files/obiavi/6157650/main_image/thumb_280x210_img-20260522-145856.jpg?ver=1790325312"`, most recently observed 2026-09-25. The current `data/leads.json` record for the same id has `photo: null` - the current lead lost a photo its own most recent scrape snapshot had. Checked all 27,283 imoti.net records this way (history's `latest.photo`/`.description` vs current lead) and this was the only instance - an isolated case, not a pattern, but a real, silent field drop worth a look in whatever step builds `leads.json` from `history.json`.
