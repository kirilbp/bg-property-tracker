**Finding 2 - imoti.net: 100% of listings (26,804 of 26,804 in `data/leads.json`) are mislabeled `category: "apartment"`, including garages, houses, and land, because the classifier is fed the wrong language.**

- `scraper.py` (imoti.net) crawls `https://www.imoti.net/en/obiavi/r/prodava` - the *English* version of the site - and calls `classify_category(title)` (`geo_utils.py:243`) on that scraped English title.
- `classify_category()`'s keyword table (`CATEGORY_KEYWORDS`, `geo_utils.py:55-65`) is Bulgarian-only ("къща", "парцел", "гараж", etc.). An English title can never match any of it, so every single imoti.net listing silently falls through to the function's own documented default, `"apartment"`.
- This isn't a scoping non-issue like the already-documented bcpea.org case (`classify_category()`'s own docstring says the "apartment" default is "correct for every portal already scoped to an apartments-only search URL") - imoti.net's search URL is explicitly *not* apartment-scoped: the scraped listing URLs themselves contain 20+ distinct property-type path segments (`garaj` 279, `parcel` 1932, `kashta` 938, `zemedelski-imot` 119, `magazin` 431, `ofis` 408, `sklad` 54, `gora` 5, `fabrika` 4, `hotel` 22, etc.).
- Proof via the record's own internal contradiction (no portal fetch needed - the title is itself the scraped source text): e.g. `id: 6270543`, `url: https://www.imoti.net/en/obiava/prodava/varna/m-t-borovec-ug/kashta/6270543/...`, `title: "House, 236 м 2 Varna, locality Borovets sauth"`, stored `category: "apartment"`. Same pattern for `id: 6104958` (title "Development land, 5483 м 2 Sofia, Voynegovtsi", category "apartment") and `id: 5855450` (title "Agricultural land, 43962 м 2 Bourgas, Cherno more", category "apartment"). Direct WebFetch to imoti.net was blocked today (see environment note), but the title field is itself the scraper's own extraction from the source page, so this is a same-record contradiction, not a guess.
- Scale: at minimum 4,916 of 26,804 listings (18.3%) carry a non-apartment type word in their own scraped title/URL and are nonetheless bucketed "apartment" - meaning they show up under the live site's "Flats" filter and never under "Houses"/"Land"/"Garages"/"Shops"/"Business", despite the app's `typeFilterBucket()` machinery in `index.html` explicitly relying on `category` being accurate for every portal except bcpea (bcpea gets its own documented workaround via `BCPEA_TYPE_LOOKUP`; imoti.net has no such workaround and isn't flagged as needing one anywhere in `docs/decisions.md`).
- Contrast: `data/leads_olx.json` and `data/leads_imot.json` use the same `classify_category()` against equally non-apartment-scoped search URLs but still show real category diversity (olx.bg: 61% apartment/18% house/18% land/3% commercial; imot.bg: 82%/8%/5%/4%) because those scrapers keep the Bulgarian title - confirming the root cause is specifically imoti.net's `/en/` URL choice, not a flaw in the keyword approach itself.
