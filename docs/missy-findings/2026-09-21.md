## Finding: scraper_alo.py's main grid crawl has been silently dead for 5+ days — every one of alo.bg's 87,979 listings is now mismarked "removed", and that's already flowing into incorrect "Sold" status on the live site

**Evidence (from `data/leads_alo.json`, `data/history_alo.json`):**
- 100% of alo.bg's 87,979 listings have `source_status: "removed"`. Zero are `"active"`.
- A random sample of 5 listings (e.g. `alo_11099583`, `alo_10268920`, `alo_10873263`, `alo_10454642`, `alo_11307917`) all carry the *identical* `removed_at` timestamp `2026-09-16T07:57:07.690539+00:00`.
- Across the full file, 77,625 of 87,979 (88.2%) share that one timestamp; the remaining are spread across a handful of earlier dates (Sep 1, Sep 6-9, Aug 23-30) — these are the timestamps of the last few times the grid crawl actually completed a full pass, not per-listing staleness.
- The most recent `removed_at` anywhere in the file is that Sep 16 timestamp — **133.6 hours (5.6 days) old** as of now (2026-09-21).
- Every other portal, by contrast, looks healthy: their most recent `removed_at` is only 24-28 hours old (matching the 6-hourly `scrape.yml` cadence), and their overall removed-share is 8-27%, not 100%:
  - bazar: removed=27,033/50,182 (12.6% share on dominant ts), most recent removed_at age 24.0h
  - bcpea: removed=885/2,218, age 28.1h
  - homes: removed=6,514/73,815, age 25.1h
  - imot: removed=7,671/26,019, age 24.7h
  - imoti_bg: removed=90/906, age 28.1h
  - olx: removed=21,179/36,004, age 24.1h

**Root cause, from the code:** `scraper_alo.py`'s `GONE_AFTER = timedelta(hours=48)` (line 481) flips a listing to `"removed"` once its last real grid-crawl snapshot (`rec["snapshots"][-1]["seen_at"]`) is more than 48h old. Since the last successful full run of `fetch_listings()` (the actual grid crawl in `scraper_alo.py`, run via `scrape-large.yml`'s daily `0 3 * * *` cron) was Sep 16 07:57 UTC, and nothing has refreshed it since, the entire portal's data has aged 2.7x past that threshold — so literally everything alo.bg tracks now reads as gone, correctly reflecting the threshold logic but incorrectly reflecting reality, because the crawl itself has stopped producing data, not because 88k listings all vanished from alo.bg in the same 5 days.

This is silent because `scrape-large.yml`'s `scraper_alo.py` step has `continue-on-error: true` and the commit step runs `if: always()` — so a crawl that's failing/producing nothing still yields a green workflow run, every day, with nothing to distinguish it from a normal one. (Separately, and only as an aside since I'm not tasked with root-causing: `git log -- data/history_alo.json`/`scraper_alo.py` is itself misleading about when things last changed, because the workflow's rebase-conflict fallback does `git checkout --ours` during an active `git rebase` — which keeps the *upstream* version, not the local run's, the opposite of merge semantics — so real alo.bg data updates have landed bundled under unrelated commit messages like "Backfill imoti.net listing details". I only mention this because it cost real effort to confirm the timeline; it's a git-log-hygiene wrinkle, not the bug itself.)

**Confirmed downstream impact, from `sync_to_supabase.py:773`:**
```python
status = "sold" if all(s.get("source_status") == "removed" for s in sorted_sources) else "available"
```
A merged listing's live-site status is `"sold"` only when *every* one of its cross-posted sources shows `source_status: "removed"`. Since alo.bg now unconditionally reports `"removed"` for everything, any listing whose only tracked source is alo.bg (not also cross-posted on homes.bg/imot.bg/olx.bg/bazar.bg/bcpea/imoti.bg) is now being shown as **Sold** on imotenradar.com and dropped from "available" filters/sort — even though there's no real evidence any of these actually sold; the scraper just stopped running. Listings that are cross-posted elsewhere won't flip to "Sold" overall, but per `index.html` line 3447-3448 they'll each still carry an incorrect "Removed from alo.bg" badge.

I could not independently re-confirm live-on-alo.bg status for the sampled IDs today because `www.alo.bg` itself was in the blocked-domain set (see caveat above) — but the internal evidence (single mass timestamp shared by 88% of the portal, 100% vs. 8-27% removed-rate contrast against every healthy portal, and 133.6h vs. every other portal's ~24h freshness) is self-consistent and doesn't depend on that external check.

**Where to look:** `data/leads_alo.json`, `data/history_alo.json`, `scraper_alo.py` lines 467-531 (`GONE_AFTER`/`compute_leads`), `.github/workflows/scrape-large.yml` (the `scraper_alo.py` step and its `continue-on-error: true`), `sync_to_supabase.py` line 773.
